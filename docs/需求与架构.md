# SMSBot 短信管理平台：需求与架构

本文保留需求与设计依据。第一版已实现，实际启动方式和当前边界以根 README、固件烧录流程及验证记录为准。固件先采用 Wi-Fi 联网，蜂窝数据接入未实现。QQ 按 QQ 邮箱实现，不包含 QQ 聊天机器人。

2026-10-15 流程修订：当前使用“添加手机号 → 签发唯一永久 API Key → 设备随时激活”。手机号 Key 同时用于设备和外部程序，手动删除或重置才失效，不需要限时配对。下面有关配对码与独立设备 Key 的章节仅保留旧版设计背景，当前接口及升级步骤以 [API 使用方法](API使用方法.md) 为准。

## 1. 项目目标与范围

使用 LILYGO T-SIM7670G-S3（ESP32-S3 + SIM7670G）收发 SIM 卡短信，由自托管平台集中保存、按电话卡管理，并自动转发通知。

第一版建议采用单管理员、多设备、多电话卡模式。平台支持手机与桌面浏览器。每块板同一时间管理实际插入的 SIM 卡；换卡后历史短信仍归原卡，不按设备混在一起。

必须交付：Python 后端、React + TypeScript + Vite 前端、pnpm 包管理、独立 ESP32 固件目录、根目录 Dockerfile、配置示例及运行说明。Dockerfile 按用户要求编写但不进行构建或运行测试。

## 2. 已确定的技术方案

| 层 | 方案 | 用途 |
| --- | --- | --- |
| 后端 | FastAPI + SQLAlchemy + AQ-DBMigration | API、持久化、版本化 SQL 迁移 |
| 数据库 | PostgreSQL + psycopg | 独立数据库服务，使用环境变量配置连接 |
| 后台任务 | FastAPI 内置 APScheduler，共用数据库 | 持久化转发队列、失败重试、任务状态清理 |
| 前端 | React + TypeScript + Vite + pnpm | 响应式管理界面 |
| 组件与样式 | shadcn/ui + Tailwind CSS（已确认） | 按需添加组件，统一表单、弹窗、列表、手机布局 |
| 固件 | PlatformIO + Arduino / C++ | 模组通信、收发短信、平台 API |
| 部署 | 多阶段 Dockerfile + Nginx + 进程管理器 | 单容器内运行静态前端和带定时任务的 API |

数据库操作保持短事务，网络请求不能占用数据库行锁。应用前后端部署在同一容器，后台任务由 API lifespan 管理，PostgreSQL 使用外部服务或独立数据库容器。任务领取使用事务和 `FOR UPDATE SKIP LOCKED`，配合租约与唯一约束支持并发任务执行器；数据库迁移只由指定启动步骤执行，完成后再启动 API 及其内置调度器。

配置约定见 [环境变量与部署](环境变量与部署.md) 和根目录 `.env.example`。开发时读取根目录 `.env`，进程环境变量优先于文件；生产支持 `docker run --env-file` 或 `-e` 注入，不将 `.env` 写入镜像。`DATABASE_URL` 保存不带账号密码的连接地址，`DATABASE_USER`、`DATABASE_PASSWORD` 单独提供，由后端安全组合。

## 3. 管理端功能

### 3.1 登录与二次验证

- 用户名、密码登录，强制启用标准 TOTP，兼容 Google Authenticator 等验证器。
- 首次安装通过部署端初始化管理员，禁止公开注册与默认密码。
- 首次登录进入受限的 2FA 绑定流程，提供二维码、手动密钥；验证一次动态码后才能进入管理界面。
- 后续登录必须同时完成密码和动态码验证；限制失败次数，防止重复使用同一时间步的动态码。
- 提供一次性恢复码，只展示一次，服务端存摘要；重置 2FA 需要密码和动态码或恢复码。
- 使用 HttpOnly 会话 Cookie，生产环境启用 Secure、SameSite 和 CSRF 校验；退出后撤销会话。
- 密码使用 Argon2id 等密码哈希；TOTP 密钥与通知凭据加密保存，加密主密钥来自部署环境。

### 3.2 总览与电话卡管理

- 总览：电话卡数量、在线设备、今日收信、待发短信、转发失败数量。
- 卡片：名称、手机号、ICCID、运营商、信号、SIM 状态、网络注册状态、所属设备、最后在线时间。
- 电话卡以 ICCID 唯一识别；手机号允许手动填写或纠正，自动读取失败显示“未设置”。
- 允许编辑名称、备注和手机号，查看该卡收件箱、发件箱、转发设置。
- 显示设备状态和电话卡状态两个维度，例如“设备在线，但 SIM 未就绪”。
- 建议状态心跳 30 秒一次，超过 90 秒无心跳显示离线；界面显示状态采样时间，避免旧信号看起来像实时值。
- API Key 可撤销、轮换；卡片换到另一设备需要管理员重新绑定，避免静默覆盖原设备。

### 3.3 收件箱

- 按电话卡分类，支持全部卡片、关键词、发件号码、时间、转发状态筛选及分页。
- 显示发件人、短信正文、卡片、模组接收时间、平台接收时间与各通道的转发状态。
- 支持详情、复制正文、单条删除、批量删除、失败转发重试。
- 中文、英文、数字、长短信需要正确解析；长短信重组后再转发，不把每个分片当完整短信。
- 删除短信同时取消未执行的转发任务；已投递给第三方的通知不能撤回。

### 3.4 发件箱

- 选择已绑定、支持发送的电话卡，填写收件号码与正文，创建发送任务。
- 发件号码来自所选 SIM 卡，不能任意伪造号码；手动填写的卡片手机号只是管理标签。
- 记录收件号码、正文、电话卡、创建时间、领取时间、模组提交时间、状态和错误。
- 状态：待发送、设备已领取、发送成功、发送失败、结果未知、已取消。
- 未领取任务允许取消或删除；已领取任务不能保证及时取消，不允许通过删除掩盖执行状态。
- 已完成的记录可删除；结果未知的任务只允许明确提示后的人工重发，并创建新的关联记录。
- “发送成功”定义为模组确认提交成功，不等同于收件人收到；若支持状态报告，可额外记录已送达。

### 3.5 通知通道与规则

| 通道 | 配置 |
| --- | --- |
| QQ 邮箱 | SMTP 主机、端口、TLS 模式、账号、授权凭据、收件人 |
| Gmail | SMTP 主机、端口、TLS 模式、账号、适用的应用密码或认证方式、收件人 |
| 通用邮件 | 自定义 SMTP 配置 |
| Bark | 服务地址、设备 Key、可选分组和声音 |
| PushDeer | 服务地址、PushKey |

QQ 邮箱、Gmail 属于 SMTP 通道的配置预设，不是三个独立发送引擎。若用户所说的 QQ 指聊天消息，需要单独确认机器人接入方式。

- 一个电话卡可以绑定多个通道；通道支持启用、停用、编辑、删除和测试通知。
- 第一版按卡配置“收到所有短信时转发到选定通道”；关键词规则可作为后续扩展。
- 每条短信对每个目标通道独立记录任务和结果，一个通道失败不影响其他通道。
- 默认模板包含卡片名称/号码、发件人、接收时间和正文。
- 修改规则仅影响之后收到的短信；历史短信通过显式重试或补发操作处理。
- 凭据不在日志、URL 或列表接口中明文展示；配置编辑时返回掩码，空值表示保持原凭据。

## 4. 设备注册与身份

1. 管理员在平台创建短期配对码，写入固件配置。
2. ESP32 读取设备标识、模组信息与 ICCID，SIM 就绪后发起注册。
3. 服务端验证配对码，绑定设备与电话卡，返回 device_id、sim_id、API Key、poll_interval_ms 和 heartbeat_interval_ms。
4. ESP32 将凭据持久化到 NVS，重启后直接使用，不重复注册。
5. 服务端仅保存 API Key 摘要；凭据限定设备和当前卡片，不允许读取其他卡的任务。
6. 换卡时暂停旧卡任务，重新配对绑定新卡；保留旧卡记录。

首次注册需携带持久化 registration_request_id。为应对“服务端注册成功、响应丢失”，服务端在短时窗口内允许同一请求安全取回同一结果；临时返回凭据需加密存储并过期清理。不能简单用一次性配对码使设备丢失响应后永久无法恢复，也不能凭公开 ICCID 领取已有 Key。

## 5. 收信与自动转发流程

```text
SIM7670G 收到短信
  → ESP32 解析短信并保存稳定的 event_id 和待上传内容
  → 使用 API Key 上传
  → 后端事务内写短信，并创建每个目标通道的转发任务
  → 提交成功后返回确认（重复上传返回同一结果）
  → ESP32 清理已确认的本地缓存及对应模组短信
  → worker 领取到期任务、发送通知、保存结果
```

- 唯一约束采用 `(device_id, event_id)`；不能只按正文去重，否则相同验证码或重复通知可能被误删。
- event_id 在首次读取后持久化，重启和重试不能重新生成；必须处理 SIM 存储索引复用。
- 断网期间保留模组短信或本地持久化队列，恢复后补传；平台确认前不能删除唯一副本。
- 处理短信缓存满、部分长短信缺失、解析失败等情况，提供状态或错误上报。
- worker 使用任务领取租约，服务重启后恢复未完成任务，不能只依赖进程内定时列表。
- 转发失败按指数退避重试，例如 10 秒、30 秒、2 分钟、10 分钟、30 分钟；达到上限转为失败并支持人工重试。
- 通知通道未提供幂等机制时，发送成功但确认丢失可能造成重复通知；转发语义为至少一次，不能承诺绝对不重复。

## 6. 发信轮询与状态机

```text
用户创建发信任务 → pending
设备每 1 秒请求领取任务 → leased
设备持久化任务 ID 与发送阶段 → 调用模组发送
模组明确成功 → 回执 sent
模组明确拒绝 → 回执 failed
发送阶段断电或结果无法确认 → unknown
```

- 默认轮询 1000ms，可配置；请求失败时退避并加入随机抖动，恢复后回到正常间隔。
- 领取操作使用 POST，并在事务内原子更新；同一任务不能被两个请求同时领取。
- 返回唯一 attempt_id / lease_token；回执同时验证任务、设备、SIM、尝试标识。
- 发信任务和回执均支持幂等。设备记录已执行任务及结果，重复领取时补交回执，不再次发短信。
- 领取后尚未调用模组，若设备能可靠确认未发送，可重新排队；无法确认的超时任务进入 unknown，禁止直接自动重发。
- 发短信与保存发送结果无法形成同一事务，所以断电边界不能保证严格 exactly-once；以避免自动重复发信为优先。
- 设备回执上传失败时持久化重试；迟到回执须按 attempt_id 校验，不能覆盖其他尝试的最终状态。
- 中文与长短信采用正确编码和分段，平台显示可能产生多条计费短信；分段部分成功时记录部分结果，不能无条件重发全文。

## 7. 建议数据模型

| 表 | 主要内容 |
| --- | --- |
| users | 用户名、密码摘要、加密 TOTP 密钥、绑定状态 |
| sessions / recovery_codes | 会话、过期时间、一次性恢复码摘要 |
| pairing_codes | 配对码摘要、有效期、消费记录 |
| devices | 设备标识、Key 摘要、固件版本、最后在线时间 |
| sim_cards | ICCID、手机号、名称、运营商、当前设备、状态 |
| device_registrations | 注册请求幂等与短期响应恢复信息 |
| incoming_sms | 设备 event_id、电话卡、发件人、正文、各时间字段 |
| outgoing_sms | 电话卡、收件人、正文、状态、创建与完成时间 |
| send_attempts | 发送尝试、领取令牌、阶段、错误、模组消息引用 |
| notification_channels | 通道类型、普通配置、加密凭据、启用状态 |
| sim_channel_bindings | 电话卡与通道绑定 |
| forwarding_jobs | 短信、通道、状态、尝试次数、下次重试、租约 |
| audit_events | 登录、配对、Key 撤销、配置变更、删除等操作记录 |

所有时间以 UTC 保存，前端按浏览器时区显示。ICCID、设备事件、通道投递任务添加适当唯一约束，队列查询和卡片时间排序添加索引。审计日志不保存短信正文或密钥。

迁移使用用户指定的 AQ-DBMigration，依赖声明在 `backend/pyproject.toml`，初始 SQL 位于 `backend/resource/db_migration/V1__init.sql`。新建库 baseline 为 0，后续结构变更只添加新的版本 SQL；已执行文件不可修改、重命名或移动。具体接入与异常恢复约束见 [数据库迁移](数据库迁移.md)。禁止同时使用其他迁移框架或 ORM `create_all()` 修改结构。

初始表结构保留删除记录的幂等标识：删除收发短信时，应用清空正文、号码等内容并标记 `deleted_at`，保留 ID 与事件/请求标识，防止迟到重试重新创建短信。取消待发任务后才可删除；通道删除前停用并取消未执行任务。API 和 worker 已过滤已删除记录。

## 9. 固件实现要求与硬件边界

- 使用准确的板型定义，普通 T-SIM7670G-S3 与 Standard 版本不共用未经核实的引脚配置。
- 初始化电源控制、串口与模组；读取 ICCID、SIM 就绪状态、运营商、网络注册与信号。
- 串口通过统一任务管理，区分命令响应与异步通知，避免发信、收信、心跳查询争用串口。
- 实现网络重连、API 请求超时、证书校验、时间同步、配置及队列持久化。
- 收信处理必须覆盖 PDU/Unicode、长短信分片和重组；不能仅用按行读取文本的演示程序替代。
- SIM 不支持自动提供本机号码时，平台提示手动填写；信号未知用 null / 未知显示，不显示满格。
- 当前实现 Wi-Fi 联网；后续若增加蜂窝流量，需要额外配置 APN，并验证模组数据连接与短信并发。
- 实机验收需用实际 SIM 卡确认当地运营商及模组固件支持短信收发。官方文档对部分固件特别注明 SMS over SGS 条件，不能只因 LTE 联网成功就认定短信可用。

硬件依据：[LILYGO 官方普通版说明](https://github.com/Xinyuan-LilyGO/LilyGo-Modem-Series/blob/main/docs/en/esp32s3/sim7670g-s3/README.MD)、[Standard 版本说明](https://github.com/Xinyuan-LilyGO/LilyGo-Modem-Series/blob/main/docs/en/esp32s3/sim7670g-s3-standard/README.MD)。

通知接入依据：[Bark 官方仓库](https://github.com/Finb/Bark)、[PushDeer 官方仓库](https://github.com/easychen/pushdeer)。实现时再核对具体请求字段与认证响应，检查业务错误而不只检查 HTTP 状态。

## 10. 手机与桌面 UI

- 桌面侧栏，手机底部导航或抽屉；核心页面为总览、电话卡、收件箱、发件箱、设置。
- 手机短信采用卡片列表，详情与发信表单适配窄屏；桌面使用带筛选的表格与详情面板。
- 短信长文本自动换行，验证码可复制，所有操作具有加载、成功、失败反馈。
- 发送前展示所选 SIM 与目标号码；批量删除确认显示记录数量。
- 设备离线、SIM 异常、转发失败、发送结果未知具有明确不同的状态提示。
- 采用简洁现代视觉、统一留白和圆角，提供键盘操作、可见焦点、标签及足够对比度。
- 短信按纯文本渲染，不能直接解释 HTML。

组件选型已确认使用 shadcn/ui + Tailwind CSS：组件源代码按需加入项目，布局使用响应式样式；只添加实际使用的表单、按钮、对话框、抽屉、选择器、表格等。组件依赖仍会产生 JavaScript 体积，应以正式构建产物衡量轻量程度。不同时引入其他完整组件库。资料：[shadcn/ui](https://ui.shadcn.com/docs)、[Tailwind Vite 接入](https://tailwindcss.com/docs/installation/using-vite)。

## 11. Docker 交付设计

- 根 Dockerfile 分阶段：Node + pnpm 安装锁定依赖并构建前端；Python 运行阶段安装后端依赖，复制前端产物。
- 单容器运行 Nginx 和 API；API lifespan 管理定时任务，进程管理器处理退出、信号与异常重启。
- 暴露前端 8080、后端 8000。前端访问同源 `/api`，由 Nginx 代理到后端。
- 生产部署外层提供 HTTPS；设备 API 不允许通过公开明文网络传递 Key。
- PostgreSQL 独立部署，其数据目录挂载数据库持久化卷或使用托管数据库；应用容器不保存数据库文件，日志输出标准输出。
- 使用环境变量提供数据库 URL、用户名、密码、应用密钥、凭据加密密钥和初始化配置；提供 `.env.example`，真实 `.env` 不提交、不打包到镜像。
- 备份需同时保留数据库和加密主密钥，否则无法恢复通知凭据与 TOTP。
- `.dockerignore` 排除 `.env`、数据库备份、固件编译产物、node_modules 和密钥。
- 按用户要求不执行 Docker 构建、运行测试，交付说明须明确这一点。

## 12. 开发顺序与验收

1. 后端数据模型、迁移、管理员初始化、密码 + TOTP、设备配对。
2. 收信接口、幂等去重、持久化转发 worker 与三类通道。
3. 发信队列、原子领取、回执、异常恢复与取消规则。
4. 手机/桌面前端与全部管理操作。
5. 固件注册、状态心跳、收发短信、缓存与断网恢复。
6. 前后端测试、固件编译与实机联调；编写 Dockerfile、部署说明及 [固件烧录流程](../firmware/烧录流程.md)。

验收重点：

- 未完成 2FA 不可访问管理数据；错误密码/验证码受限，恢复码仅能使用一次。
- 未配对设备不可注册；错误或已撤销的 Key 无法调用设备接口；设备不能跨卡读取任务。
- 同一设备事件重复上传只创建一条短信及每通道一条转发任务。
- 数据库或程序重启后待转发任务不丢失；不同通道失败互不影响。
- 两个并发领取请求不会领走同一发信任务；重复回执不会重复发送。
- 模组成功而 API 回执丢失时，设备重传结果；无法判断是否已发送时进入结果未知。
- 换卡后不使用旧卡的 Key 与待发任务；离线时界面显示最近状态时间。
- 中文、长短信、重复正文、断网补传、设备断电、短信存储满均需验证。
- 删除操作与转发/发送执行之间的竞态有明确处理，进行中的外部发送不能承诺撤回。
- 手机宽度下可完成登录、绑 2FA、查短信、发短信、配通道与删除操作。
- Docker 测试不属于本次要求；没有实机时不能声称硬件收发已通过验证。
