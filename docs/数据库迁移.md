# 数据库迁移

采用 [AQ-DBMigration](https://github.com/nanshens/AQ-DBMigration)，固定 `1.0.2`。脚本在 `backend/resource/db_migration/`：

- `V1__init.sql`：业务表、外键、唯一约束与索引。
- `V2__runtime_guards.sql`：认证限流、设备状态、发送结果幂等字段。

后续新增更高整数版本 SQL，英文小写描述，例如 `V3__add_column.sql`。已经部署的文件不可修改、重命名、移动，不用 ORM `create_all()` 或其他迁移框架。

## 执行

按 README 配置环境、安装后端，然后执行：

```sh
python -m app.migrate
```

执行器在 `backend/app/migrate.py`，首次 baseline 为 `0`，历史表是 `migration.aq_db_migration`。

## 本项目适配

上游 1.0.2 默认分别提交 SQL 和历史。本项目 `AtomicMigration` 覆盖私有连接/执行/关闭钩子，保留上游读取、排序和校验逻辑：

1. 在创建历史表前取得事务级 advisory lock，最多等待 60 秒。
2. 本次所有 SQL 与历史记录在同一事务提交，失败整体回滚，关闭连接。
3. 允许的 PostgreSQL TLS 参数传给 psycopg2，未知参数在配置加载时拒绝。
4. 校验 V1 存在、命名、重复版本、历史文件缺失、绝对路径变动和补插旧版本。
5. 失败阻止应用启动，不静默跳过。

SQL 内不能自行 `BEGIN/COMMIT/ROLLBACK`，也不能写要求事务外执行的语句（如 `CREATE INDEX CONCURRENTLY`）。此类需求需单独设计运维步骤。

适配依赖 1.0.2 的私有方法名，升级 AQ 前必须跑迁移回归测试，不能仅修改版本直接部署。

## 固定绝对路径

上游的历史与校验包含绝对路径。容器固定 `/app/backend/resource/db_migration`，同一数据库始终从相同路径迁移。

Windows 本地路径迁移过的数据库不能直接切换到 Linux 容器；执行器拒绝路径不一致以避免重复建表。正式库从第一次就使用容器路径，数据库恢复后也保持该路径。

必须改路径时，先备份、核对历史版本与内容，再设计路径及校验值转换；不能删除历史表或提高 baseline 绕过错误。

## 验证与启动

PostgreSQL 测试已验证重复执行不重建、路径变化拒绝、重复版本拒绝，以及迁移失败时结构和历史一起回滚。测试库约束见根 README。

Docker 的 `app.start` 等待数据库并迁移，成功后再启动 API、worker 和 Nginx。镜像复制整个 SQL 目录。Docker 构建/运行按用户要求不测试。
